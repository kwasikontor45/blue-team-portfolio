[ overview ]
The Wazuh lab (see the SOC Lab Build write-up) is a deliberately-built, deliberately-exposed research environment. This is the opposite kind of project: the actual defense running on the machine I use every day. It started as a handful of one-off scripts and grew into a real personal ops platform — around 55 tracked tools, a periodic self-heal watchdog, an intrusion detection stack, DNS-layer threat filtering, and a GUI control panel I designed and built myself to run all of it without needing a terminal open.
The design principle running through all of it: automate what should never depend on me remembering to check it, and fail loud instead of failing silent. A drifted config, a stopped watcher, a broken symlink — all of it gets caught on a schedule, not discovered later by accident.

[ components ]
SELF-HEAL
Automated Health Watchdog
~25 checks, scheduled + on-demand
Runs a battery of health checks on a schedule — intrusion-prevention services, DNS resolver state, failed systemd units, log watchers, cloud-lab guardrails (idle-cost backstop, conflict detection) — and either fixes what it safely can or flags it for a human to look at. Deliberately does not auto-recreate a tool that's gone missing entirely: "missing" is ambiguous — accidentally deleted, or intentionally retired — and silently resurrecting something that was deliberately killed off is worse than leaving a gap flagged for review.
● systemd timer, real remediation + a written run log every cycle
IDS/IPS
Intrusion Detection + Prevention Stack
Suricata · Sagan · EveBox · fail2ban · ClamAV · rkhunter
Network-layer detection (Suricata) feeding log-correlation (Sagan) and a triage UI (EveBox), plus fail2ban for brute-force response, and scheduled ClamAV/rkhunter sweeps. All watched by the self-heal watchdog above — a stopped IDS process is treated as a real incident, not background noise.
● all four watcher services independently monitored
DNS-FILTER
DNS-Layer Threat Filtering
NextDNS, with an automated repair path
Network-wide DNS-layer filtering/telemetry, with its own self-heal check: if the resolver daemon drops or routing silently reverts to an unfiltered path, it gets caught and restarted on the next cycle instead of leaving the network unfiltered until someone notices.
● checked every self-heal cycle
SOT
Infrastructure-as-Code Discipline
Source-of-truth tracking for ~55 scripts
Every tool lives in one git repo and is symlinked into the live execution path — editing either copy edits the same file, so git status always tells the truth about what's actually changed. A drift check catches broken symlinks or out-of-sync permissions; non-symlinkable state (crontab, systemd units, sudoers fragments) gets explicit snapshot/diff/install commands instead of being edited blind. Pushes to two independent GitHub remotes on every change, plus an encrypted offline mirror, so there's no single point of failure for the tooling itself.
● zero drift = the repo IS the live config, not a stale copy of it
GUI-PANEL
Control Panel with Its Own Test Suite
Python / Tkinter, class-based (Runner / Poller / View)
A desktop control panel over the whole toolkit — live status tiles, category-organized action buttons, a shared output console — so day-to-day operation doesn't require memorizing CLI flags. Structured around a small number of reusable pieces: one component that runs every command safely (own process group, no pipe a stray child can hold open, hard timeout), one that lets background threads talk to the UI thread safely, one that manages recurring poll jobs per screen. Ships with a --selftest flag that builds every screen headless and fails on any UI callback error or a poll job that outlives its screen — run after every change, not just hoped to still work.
● selftest builds all 15 screens clean before any change ships

[ real bugs found and fixed — not hypothetical ]
A few, picked because each one only got caught by actually testing the fix, not by assuming a standard API would behave as documented:
FIXTaskbar showed a generic icon instead of the app's own — root cause was a 256×256 image handed to the X11 icon property, which silently fails above a size limit (confirmed via xprop: empty property at 256px, correct one at 48px). Not a permissions or config issue, just a size ceiling nothing warns you about.
FIXBuilt a maximize button using the standard cross-platform toggle API — then tested it directly (no UI click, just the raw call + a geometry check) before shipping, and found it's a silent no-op on this window manager: no error, no state change, just nothing happens. Replaced with a manual geometry calculation against the desktop's real usable area, confirmed working the same rigorous way.
FIXA one-time "grow the console on first use" feature marked itself done before confirming the resize actually succeeded — a failed first attempt (window not fully drawn yet) would have silently disabled the feature for the rest of the session. Fixed the ordering so it only marks done after a real, verified attempt.
FIXA listening-services security check had two bugs stacked on each other: a loopback-exclusion regex anchored against the wrong part of the line (never matched, so localhost-only services were false-flagged as network-exposed), and a second "must be a wildcard bind" filter that matched every line regardless of actual bind address — silently doing nothing. Root-caused both by testing the actual tool output line-by-line instead of trusting the logic on read.
